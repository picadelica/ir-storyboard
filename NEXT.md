Два содержательных решения внутри, а не просто пересказ команд:

1. **Уровень доступа B — код + деплой, но без shell на проде.** Деплой идёт через workflow,
   поэтому SSH на сервер для него не нужен. Оркестратор слушает только на `127.0.0.1:5000`,
   значит нужен проброс порта — и ровно он один. Ключ выдаётся строкой
   `restrict,port-forwarding,permitopen="127.0.0.1:5000",command="/bin/false"`: проброс есть,
   shell'а нет, другие порты недоступны. Приём подсмотрен у vitalis (узкий ключ с `command=`).
2. **Схема веток изменена — вдвоём по-старому нельзя.** Раньше коммитили прямо в `feat/v2`,
   но из неё же тянет деплой: промежуточный коммит одного уезжает в бой при деплое другого.
   Теперь `feat/v2` — интеграционная (только зелёное и законченное), задачи в короткоживущих
   `feat/v2-<тема>`, вливание `--ff-only` после ребейза. Правило переписано и в `CLAUDE.md`,
   где стояло просто «работаем на feat/v2».

**Два вопроса владельцу, которые я не мог решить за него:**

## Мониторинг — ЗАДЕПЛОЕН И ПРОВЕРЕН НА ЖИВЫХ ДАННЫХ

Три фазы из `~/Downloads/TASK-monitoring.md`. Воркфлоу аналитика не меняется: разбор —
тот же ингест, новых очередей и обязательных шагов нет.

**Фаза 1. Watchlist и кандидаты.** Новая вкладка «Мониторинг» в зоне Build.
- `watchlist_items` (youtube_channel | rss | search_query) + `monitor_candidates`
  (UNIQUE client_id×norm_url — повторная проверка не плодит находок).
- Обход: yt-dlp `--flat-playlist` (без скачивания), RSS/Atom на stdlib (feedparser в
  проект не тянул), поиск через тот же `llm.web_search` (Tavily).
- Перед дорогой транскрипцией — дешёвый LLM-фильтр ТОЛЬКО по метаданным →
  `relevance` likely|unclear|unlikely + одно предложение. Без ключа — стаб
  (имя спикера в заголовке → likely).
- «Разобрать» → state=ingesting и переход на обычный экран YouTube-ингеста с
  предзаполненной ссылкой (тот же приём, что у Research). Автоматически НИЧЕГО не
  разбирается. `ingested` + `source_id` проставляются сами, когда после коммита
  появляется строка `sources` с этим URL (`watchlist.link_ingested`).
- Блок «Предложения»: каналы, с которых уже брали видео этого клиента, но которых нет
  в мониторинге.
- Планировщик: свой поток внутри приложения, `MONITORING_INTERVAL_MIN` (0/пусто =
  выключен, это дефолт). Системный cron на сервере не заводили.

**Фаза 2. Обзор эпизода.** Сворачиваемый блок «Обзор» сверху на экране превью ингеста
(мотив, блоки с кликабельными таймкодами, ключевые цитаты, «между строк»).
- Таблица `digests`, идемпотентность по (эпизод × спикер).
- Спикер: единственный фаундер — автоматически; двое и больше без явного выбора →
  обзора просто нет, факты идут как всегда.
- Цитата, которой нет в расшифровке дословно → `unverified` (показываем плашкой, не
  выбрасываем: это сигнал о качестве обзора).
- Сравнение с прошлыми выступлениями спикера — вторым вызовом внутри того же job-а:
  проза для аналитика + машиночитаемые `details` (topic/kind/was/now), которые
  подаются в СЛЕДУЮЩИЕ сравнения («уже зафиксировано, не повторяй»).

**Фаза 3. Чип «возможный дубль».** Жёлтый чип на карточке факта в превью (и YouTube, и
Audio): похожие активные факты ТОЙ ЖЕ ячейки, механический скоринг (нормализация +
Jaccard ≥ 0.55, как в дедупе пайплайна, где ≥0.85 факт вообще не доходит до превью).
Клик разворачивает похожий факт: «открыть в матрице» / «не брать этот факт».

**Расхождения с ТЗ (осознанные, код был прав):**
1. `client_id` — TEXT, не INTEGER (в этой БД id клиентов текстовые).
2. `digests` ключуются по `(norm_url, speaker)`, а не `(source_id, speaker)`: строка
   `sources` появляется только на коммите, а обзор нужен уже в превью. `source_id`
   проставляется задним числом (`digest.link_source`).
3. Обзор собирается ОТДЕЛЬНЫМ job-ом с экрана превью, читая расшифровку из кэша, а не
   внутри пайплайна ингеста. Так путь фактов не тронут вообще (есть golden-тест).
4. Чип дубля не открывает диалог склейки: склеивать можно только сохранённые факты, а
   факта превью в БД ещё нет. Поэтому чип показывает похожий факт и даёт его не брать;
   склейка — как и раньше, в «Проверке фактов» после коммита.
5. `main.py` вырос не только на подключение роутера: `get_conn` переехала в
   `backend/deps.py` (иначе роутер импортирует main по кругу; объект функции тот же,
   `dependency_overrides` в тестах работает) + 3 строки старта планировщика.
6. Фазы поехали одним коммитом, а не тремя: файлы (db.py, llm.py, роутер, api.ts)
   общие для всех трёх, дробить постфактум по кускам — больше риска, чем пользы.
7. Живой цикл прогнан не на Accumulator, а на песочнице G2 — по решению владельца.

## Что показал живой прогон (и что по итогам починено)

**Фаза 1 на реальном канале.** Ссылка на видео → канал определился сам
(`@PaulBarronNetwork`), 10 находок, LLM-фильтр по метаданным пометил все `unlikely`
с внятными причинами («новостной материал о CLARITY Bill, Либерман не упоминается») —
то есть шум до аналитика не доехал.

**Поиск по имени вместо канала — на порядок точнее.** На G2 заведены оба источника,
цифры за один обход: поиск «David Liberman Gonka interview» — найдено 10, до аналитика
дошло 9 (ютуб, Spotify, подкасты, статьи; отсеян только whitepaper-PDF); канал
Paul Barron Network — найдено 15, дошло 0. Вывод: канал имеет смысл заводить, только
если это личный канал спикера или подкаст, где он постоянный участник; для остальных —
`search_query`.

**Временные границы поиска** (`config.window` у источника):
`auto` (по умолчанию) — первый обход за год, дальше «с прошлой проверки минус неделя»
(нахлёст на отставание поисковых индексов); либо явные `all` / `year` / `quarter` /
`month`. Первый обход берёт год осознанно: выступление двухлетней давности для матрицы
такой же материал, если мы его ещё не разбирали. Повторные находки бесплатны — дедуп
по `norm_url` отсекает их до LLM-вызова.

**Даты находок.** Веб-поиск отдаёт дату редко, поэтому для ютубовских ссылок она
дотягивается метаданными (и только у прошедших фильтр — за отсеянное в сеть не ходим).
У Spotify/подкаст-платформ и статей даты по-прежнему нет: хвост, если станет мешать —
парсить страницу или брать `topic="news"` у Tavily.

**Фаза 2 на двух реальных эфирах Либерманов** (Peter McCormack ~2 ч и Paul Barron 28 мин,
расшифровки взяты из кэша, повторная транскрипция не потребовалась). Обзоры содержательные;
сравнение поймало реальный сдвиг: от «у нас год-два, потом поздно» к демонстрации
работающей сети. Починено по итогам:
1. **Пустая дата эфира подменялась датой сборки обзора** → аналитик видел «было
   (сегодня)» у прошлогодней цитаты. Теперь пустая дата остаётся пустой.
2. **«Прошлым» считался любой другой эфир спикера, включая более поздний** — архив
   разбирают не по порядку, и сравнение шло задом наперёд. Появилась отсечка по дате.
3. **Даты эфира часто нет вообще** (у старых прогонов мета в превью пустая) → отдельный
   `digests.order_key`: дата выступления, иначе дата разбора. Показываем аналитику
   по-прежнему только настоящую дату.

Осталось косметическое: модель иногда ставит `timecode_sec=0` в пунктах сравнения и
однажды вставила иероглиф в русскую фразу — на глаз заметно, но правкой промпта чинить
только если будет мешать.

## Поисковые источники заведены рабочим клиентам (2026-08-04)

17 источников `search_query` на 15 клиентов — по фаундеру (или по каждому, если их
несколько), запрос «<Фаундер> <Компания> interview|интервью», окно `auto`.
Скрипт: `scripts/seed_search_sources.py` (сухой прогон без `--apply`).

Правила отбора, чтобы не плодить мусор:
- пропущены `test` (тестовый клиент) и `g2` (у песочницы свои источники);
- пропущены `explee` и `x` — ни фактов, ни фаундеров-сущностей (заготовки);
- фаундер берётся из сущностей (тогда у источника есть спикер и обзор эпизода
  привяжется к нему), иначе из `clients.founder_name`;
- имена-неимена отсеиваются: у `gonkaai` в сущностях лежит аналитикова пометка
  «Liberman siblings (…) — через Product Science как инкубатор», из неё запрос не
  построишь. Фильтр: 2-4 слова, без скобок, запятых и тире.

Первый обход: просмотрено 177, новых 166. Дальше выяснилось, что фильтр судил только
о человеке, но не о ФОРМЕ находки — в очередь лезли профили LinkedIn/Facebook, карточки
спикеров конференций, страницы «Co-Founder & COO», пресс-релизы и статьи о компании
(у Uzum такими карточками была почти вся выдача). Промпт переписан: два условия
проверяются независимо (тот ли человек И запись ли это речи), ссылка уходит в оценку
как сильный сигнал о форме. Очередь пересчитана `watchlist.reassess_candidates`
(состояние скрытых и разобранных не трогается).

## Деплой-нюансы (важно, не потерять)

1. Деплой только через workflow `deploy_ir_storyboard` (repo_path=/opt/ir-storyboard,
   branch=feat/v2, health_url=`http://172.17.0.1:80/`, projectId=ir-storyboard). Руками по
   ssh не деплоить, на сервере не коммитить. Реквизиты гейта:
   `source ~/.config/conductor-orchestrator/credentials`; паспорт —
   `PATCH http://localhost:5050/ui/api/projects/ir-storyboard/state` (X-Api-Key=ADMIN_API_KEY).
2. **Миграция схемы.** Startup-хук `_start_auth_poller` НЕ вызывает `init_schema` (частая
   ошибка в рассуждениях — не верить). Реально схему мигрирует **`get_conn` — на КАЖДОМ
   запросе** (теперь `backend/deps.py`), поэтому после деплоя новые колонки/таблицы
   добавляются при первом же обращении к /api. НО: если проверяешь прод-БД «голым»
   `db.connect()` без init_schema — увидишь старую схему и подумаешь, что сломано.
   Безопасно и сразу: после деплоя прогнать вручную
   `docker exec ir-storyboard-backend-1 python3 -c "from ir_storyboard import db; db.init_schema(db.connect('/app/data/matrix.db'))"`
   (идемпотентно). Проверять `facts_for_cell` — тоже через init'нутое соединение.
3. Прод-`/api` закрыт гейтом приложения (кука `ir_session` от Telegram-шлюза), НЕ
   Basic Auth: curl без куки отдаёт 401 — это норма, маршрут жив. Открыты `/` (health),
   `/api/health`, `/api/auth/*`. `curl -u логин:пароль` бесполезен — пароля нет.
4. Локальный dev: backend `uvicorn backend.main:app --port 8080` (БД `data/matrix.db`,
   gitignored, это НЕ прод); фронт — `npm --prefix frontend run dev -- --port 5180`
   (прокси /api→:8080). Прод-БД читать по ssh: `ssh root@216.57.108.107` →
   `docker exec ir-storyboard-backend-1 python3 …` над `/app/data/matrix.db` (только чтение!).

## Справка по «собранным» карточкам (модель данных)

Скрытый факт = `state='rejected'` + `merged_into=<id активной>`. Две природы, различаются по
`verification_note`:
- «переименован спикер → #N» — `attribute_fact` (иммутабельность: имя спикера нельзя вписать в
  текст на месте → новый факт + reject старого). НЕ мерж.
- «дубль — слит в #N» / «слит (с правкой текста) в #N» — `merge_facts` (default-fold / curated-синтез).
Инвариант #5: текст факта никогда не UPDATE-ится; любое «изменение» = новый факт, старый остаётся.
