# Онбординг второго разработчика

> Кому: разработчику, который подключается к проекту, и владельцу, который выдаёт
> доступы. Читается сверху вниз; шаги владельца и шаги разработчика помечены явно.
>
> Что уже есть в репозитории и здесь НЕ дублируется:
> `README.md` — что за система, `CLAUDE.md` — архитектурные инварианты,
> `DEPLOY.md` — развёртывание с нуля, `docs/restore.md` — восстановление из бэкапа,
> `USER_GUIDE.md` и `docs/analyst-guide.md` — работа аналитика в интерфейсе.

---

## 0. Что это за система (два абзаца, чтобы читать дальше осмысленно)

Внутренний инструмент IR-агентства. Ведёт персистентную нарративную матрицу по
каждому клиенту: 8 концентрических слоёв × 3 подсекции = 24 ячейки. Факты
тегируются `green` / `red` / `grey`, приходят из четырёх методологически
ограниченных каналов сбора, и никогда не редактируются на месте — «изменение»
всегда означает новый факт с новым `captured_at`.

Технически: чистый Python-пакет `ir_storyboard/` (ядро, без FastAPI и UI), поверх
него FastAPI (`backend/`), рядом React+TS+Vite (`frontend/`), данные — один файл
SQLite. Прод — docker compose на сервере агентства, деплой только через
оркестратор. LLM — Anthropic, веб-поиск — Tavily; без ключей всё работает на
детерминистских стабах, поэтому «запустилось и выглядит живым» ≠ «работает
правильно».

## 1. Решение владельца ДО выдачи доступов

Уровень доступа определяет всё остальное. Выбрать один:

| | Что может разработчик | Что нужно выдать | Кому подходит |
|---|---|---|---|
| **A. Только код** | писать код, гонять тесты локально | GitHub | подряд на фичу, деплоит владелец |
| **B. Код + деплой** ⭐ | всё из A + сам катит на прод через оркестратор | GitHub + узкий SSH-ключ (только туннель) + реквизиты оркестратора | **второй постоянный разработчик — рекомендуется** |
| **C. Полный** | всё из B + shell на прод-сервере | GitHub + обычный SSH на сервер | только если он же администрирует сервер |

**Рекомендация — B.** Разработчик получает самостоятельность (может катить и
откатывать), но не получает shell на машине с боевыми данными. Ключ выдаётся с
жёстким ограничением: он умеет ровно одно — пробросить порт до оркестратора.
Как это сделать — шаг 4.2.

**Уровень C не нужен для деплоя.** Деплой идёт через workflow оркестратора, а не
по SSH. Единственное, ради чего в этом проекте лезут на сервер руками, —
восстановление из бэкапа (`docs/restore.md`), а это работа владельца.

> ⚠️ **Честное предупреждение про `ADMIN_API_KEY`.** Реквизиты оркестратора
> включают админский ключ реестра, а он даёт запись в паспорта **всех** проектов
> Дмитрия, не только этого. Отдельного ключа под один проект в текущей сборке нет.
> Прежде чем выдавать — проверьте в UI оркестратора, нельзя ли завести
> пользователя с ролью `user` вместо выдачи админского ключа. Если нельзя, это
> осознанный оверграант, и о нём надо знать обеим сторонам.

## 2. Шаг 1 — GitHub: ключи и доступ к репозиторию

Репозиторий: `github.com/dechernov-stack/ir-storyboard`. Рабочая ветка — `feat/v2`,
`main` держится её зеркалом (см. §7).

### 2.1 Разработчик: сгенерировать SSH-ключ

Отдельный ключ под этот проект — чтобы его можно было отозвать, не трогая
остальные:

```bash
ssh-keygen -t ed25519 -C "ir-storyboard $(whoami)@$(hostname -s)" \
           -f ~/.ssh/id_ed25519_ir_storyboard
# passphrase — задать непустую; дальше её подхватит агент
```

Прописать в `~/.ssh/config`, чтобы git сам брал нужный ключ:

```
Host github-ir
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_ir_storyboard
    IdentitiesOnly yes
    AddKeysToAgent yes
    UseKeychain yes        # только macOS
```

Публичную часть — владельцу:

```bash
cat ~/.ssh/id_ed25519_ir_storyboard.pub
```

### 2.2 Разработчик: зарегистрировать ключ в своём аккаунте GitHub

GitHub → Settings → SSH and GPG keys → **New SSH key** → вставить содержимое
`.pub` → Add. Проверка:

```bash
ssh -T git@github-ir
# Hi <username>! You've successfully authenticated...
```

### 2.3 Владелец: выдать доступ к репозиторию

Репозиторий → Settings → Collaborators → **Add people** → GitHub-логин
разработчика → права **Write**.

- **Write, не Admin.** Write достаточно для веток, пушей и PR. Admin даёт
  удаление репозитория и смену настроек защиты — второму разработчику не нужно.
- **Deploy key не подходит** и заводить его не надо. Deploy key — это доступ
  машины, а не человека: он безымянный в истории и обычно read-only. Сервер и так
  клонирует репозиторий по HTTPS.

### 2.4 Разработчик: клонировать

```bash
git clone github-ir:dechernov-stack/ir-storyboard.git
cd ir-storyboard
git checkout feat/v2
```

### 2.5 Разработчик: поставить защиту от затирания чужой работы (обязательно)

По общим веткам пишут параллельные сессии — и человеческие, и агентские. Без
хука рано или поздно кто-то затрёт чужой push. Хук глобальный, ставится один раз
на машину:

```bash
mkdir -p ~/.config/git/hooks
cat > ~/.config/git/hooks/pre-push <<'HOOK'
#!/bin/sh
# Блокирует push, если на origin есть коммиты, которых нет локально.
# Намеренный обход (исключение, руками): git push --no-verify
remote="$1"; status=0
while read -r local_ref local_oid remote_ref remote_oid; do
  case "$local_oid" in *[!0]*) : ;; *) continue ;; esac   # пропустить удаление ветки
  branch=${remote_ref#refs/heads/}; [ -n "$branch" ] || continue
  git fetch -q "$remote" "$branch" 2>/dev/null || continue
  behind=$(git rev-list --count "$local_oid..FETCH_HEAD" 2>/dev/null)
  if [ "${behind:-0}" -gt 0 ]; then
    echo "✋ pre-push blocked: origin/$branch has $behind commit(s) you don't have locally."
    echo "   Параллельная сессия что-то запушила. git divergence → rebase → push."
    status=1
  fi
done
exit $status
HOOK
chmod +x ~/.config/git/hooks/pre-push
git config --global core.hooksPath ~/.config/git/hooks

# и удобный алиас к нему
git config --global alias.divergence '!f() { b=$(git symbolic-ref --short HEAD) || return 1; git fetch -q origin "$b"; echo "── local ahead (unpushed) ──"; git log --oneline "origin/$b..HEAD"; echo "── remote ahead (missing locally) ──"; git log --oneline "HEAD..origin/$b"; }; f'
```

Проверить: `git divergence` должен отработать без ошибки.

## 3. Шаг 2 — локальная среда

### 3.1 Зависимости

Нужны Python 3.11+, Node 20+, Docker (для сборки образов; для повседневной
разработки не обязателен).

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt      # включает requirements.txt
npm --prefix frontend install
```

Три файла зависимостей, и это не дубли:

| Файл | Что в нём | Когда нужен |
|---|---|---|
| `requirements.txt` | ядро `ir_storyboard/` | всегда (подтягивается остальными) |
| `requirements-dev.txt` | + FastAPI, uvicorn, pytest, httpx | **обычная разработка и тесты** |
| `backend/requirements.txt` | полный рантайм, включая тяжёлое ML (`faster-whisper`, `yt-dlp`) | только если трогаешь YouTube/аудио-ингест |

### 3.2 `.env` — что запрашивать у владельца

`.env` в git нет намеренно (`.gitignore`), шаблон — `.env.example`. Для локальной
разработки:

| Переменная | Нужна локально? | Что даёт |
|---|---|---|
| `ANTHROPIC_API_KEY` | **да, просить** | классификация фактов, контент циклов, обзоры эпизодов |
| `TAVILY_API_KEY` | да, если трогаешь research/мониторинг | реальный веб-поиск |
| `AUTHGW_URL` + `SESSION_SECRET` | **нет** | гейт авторизации; локально оставить пустыми |
| `DOMAIN`, `ADMIN_EMAIL` | нет | только для прод-оверрайда с Caddy |

> **Главная ловушка проекта.** Без `ANTHROPIC_API_KEY` система поднимается и
> выглядит исправной, но весь LLM-слой молча уходит в детерминистские стабы:
> факты классифицируются по ключевым словам, обзоры эпизодов — заглушки. Отладка
> «почему модель так решила» на стабах бессмысленна. Если ключа нет — знай, что
> ты смотришь на стаб.
>
> Пустые `AUTHGW_URL`/`SESSION_SECRET` локально — это не «сломано», а штатный
> режим: гейт выключен, ты входишь как `dev` с правами админа.

### 3.3 Локальная база

Локальная БД (`data/matrix.db`, gitignored) — **не копия прода**. Прод-данные на
машину разработчика не выгружаются. Наполнить пилотными данными:

```bash
.venv/bin/python -m ir_storyboard.cli seed-accumulator   # пилотный клиент
# или полный сквозной прогон: init + seed + все 3 цикла + артефакты
.venv/bin/python run_demo.py
```

### 3.4 Запуск

```bash
# backend (терминал 1)
.venv/bin/uvicorn backend.main:app --reload --port 8080

# frontend (терминал 2) — прокси /api → :8080
npm --prefix frontend run dev -- --port 5180
```

### 3.5 Тесты — до каждого пуша

```bash
.venv/bin/python -m pytest tests/ -m "not network" -q     # ожидание: 365 passed
```

Сетевой `test_youtube_e2e` исключён меткой и ходит в интернет — гонять осознанно.
Фронт собирается так (без `rm` может соврать инкрементальным кэшем):

```bash
rm -f frontend/*.tsbuildinfo && npm --prefix frontend run build
```

## 4. Шаг 3 — доступ в само приложение и к оркестратору

### 4.1 Вход в прод-интерфейс (Telegram-шлюз)

Прод закрыт не паролем, а сессионной кукой от центрального Telegram-шлюза:
`/api/*` пускает только с валидной `ir_session`. Открыты `/` (health),
`/api/health` и `/api/auth/*`.

**Владелец:** добавить Telegram-аккаунт разработчика в группу продукта
`ir-storyboard` в конфиге шлюза `tg-authgw`. Нужны админские права в интерфейсе —
дописать Telegram-id в `IR_ADMIN_TIDS` в серверном `.env` (после правки —
передеплоить, §5).

**Разработчик:** открыть прод-домен (спросить у владельца) → войти через бота.

> `curl -u логин:пароль` к `/api` не работает и работать не может — Basic Auth в
> проекте нет. `401` без куки — нормальный ответ живого маршрута, а не поломка.

### 4.2 Владелец: узкий SSH-ключ для туннеля к оркестратору

Оркестратор слушает только на `127.0.0.1:5000` прод-сервера и наружу не смотрит.
Чтобы разработчик мог запускать деплой, ему нужен проброс порта — **и больше
ничего**. Ключ выдаётся с ограничением, которое не даёт ни shell, ни доступа к
другим портам.

Разработчик генерирует и присылает публичный ключ:

```bash
ssh-keygen -t ed25519 -C "corch-tunnel $(whoami)" -f ~/.ssh/id_ed25519_corch
cat ~/.ssh/id_ed25519_corch.pub
```

Владелец дописывает его в `/root/.ssh/authorized_keys` на `216.57.108.107`
**одной строкой с префиксом ограничений**:

```
restrict,port-forwarding,permitopen="127.0.0.1:5000",command="/bin/false" ssh-ed25519 AAAA...ключ... corch-tunnel dev2
```

Что делает префикс:
- `restrict` — выключает всё сразу (pty, agent-forwarding, X11, порт-форвардинг) и
  автоматически подхватывает будущие ограничения OpenSSH;
- `port-forwarding` — возвращает обратно только проброс портов;
- `permitopen="127.0.0.1:5000"` — и только на этот адрес: другие порты сервера
  этим ключом не достать;
- `command="/bin/false"` — если кто-то всё же попросит команду или shell, он
  получит отказ.

Проверка со стороны владельца — с машины разработчика должно работать первое и
НЕ работать второе:

```bash
ssh -N -L 5050:127.0.0.1:5000 -i ~/.ssh/id_ed25519_corch root@216.57.108.107   # ок
ssh -i ~/.ssh/id_ed25519_corch root@216.57.108.107 'id'                        # должно отбиться
```

### 4.3 Разработчик: реквизиты оркестратора и туннель

Владелец передаёт **по защищённому каналу** (не в мессенджер открытым текстом,
не в issue, не в коммит) три значения. Разработчик кладёт их в файл:

```bash
mkdir -p ~/.config/conductor-orchestrator
cat > ~/.config/conductor-orchestrator/credentials <<'CRED'
GATEWAY_URL=http://localhost:5050/conductor-api
GATEWAY_AUTH=<логин:пароль basic-auth гейта — от владельца>
ADMIN_API_KEY=<ключ реестра — от владельца>
CRED
chmod 600 ~/.config/conductor-orchestrator/credentials
```

`GATEWAY_URL` указывает на `localhost:5050` — это локальный конец туннеля.
Поднять туннель (держится в фоне, иногда отваливается — тогда поднять заново):

```bash
ssh -f -N -L 5050:127.0.0.1:5000 -i ~/.ssh/id_ed25519_corch root@216.57.108.107
```

Проверка, что всё сошлось:

```bash
source ~/.config/conductor-orchestrator/credentials
curl -s -o /dev/null -w "UI: %{http_code}\n" http://localhost:5050/ui/                      # 200
curl -s -H "X-Api-Key: $ADMIN_API_KEY" http://localhost:5050/ui/api/projects/ir-storyboard \
  | head -c 200                                                                             # паспорт проекта
```

Если `curl` даёт `exit 7` — туннель отвалился, поднять заново.
UI оркестратора в браузере: `http://localhost:5050/ui/projects/ir-storyboard`.

## 5. Шаг 4 — как выкатить на прод

### 5.1 Железные правила

1. **Деплой только через workflow `deploy_ir_storyboard`.** Руками по SSH —
   нельзя: теряется история деплоев и health-контроль.
2. **На сервере не коммитить.** Деплой делает `git reset --hard origin/feat/v2` —
   любая локальная правка на сервере будет молча уничтожена следующим деплоем.
   Хотфикс = коммит в репозиторий и деплой, других путей нет.
3. **Ворота (Approve в UI) не подтверждать без явного «да» владельца.**
4. **`input.projectId` обязателен** в любом запуске workflow.

### 5.2 Перед деплоем

```bash
git divergence                                            # origin не ушёл вперёд
.venv/bin/python -m pytest tests/ -m "not network" -q     # 365 passed
rm -f frontend/*.tsbuildinfo && npm --prefix frontend run build
git push origin feat/v2
```

Деплой всегда тянет `feat/v2` с origin. Значит **всё, что попало в `feat/v2`,
считается готовым к выкатке** — незаконченное туда не пушим (см. §7).

### 5.3 Запуск

```bash
source ~/.config/conductor-orchestrator/credentials
curl -s -u "$GATEWAY_AUTH" -X POST "$GATEWAY_URL/workflow" \
  -H 'Content-Type: application/json' -d '{
  "name": "deploy_ir_storyboard", "version": 1,
  "correlationId": "claudecode-<кратко-суть>",
  "input": {
    "projectId": "ir-storyboard",
    "repo_path": "/opt/ir-storyboard",
    "branch": "feat/v2",
    "health_url": "http://172.17.0.1:80/"
  }}'
# → в ответе execution_id (UUID)
```

Шаги внутри: `git_pull` → `build` → `deploy` → `health_check` → уведомление +
отметка деплоя в паспорте. При падении отрабатывает `send_failure_notification`.

Статус:

```bash
curl -s -u "$GATEWAY_AUTH" "$GATEWAY_URL/workflow/<execution_id>" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); print(d['status']); \
    [print(' ', t['referenceTaskName'], t['status']) for t in d['tasks']]"
```

Есть и CI-workflow `test_ir_storyboard` (тот же `git_pull` + `pytest -m "not
network"` в одноразовом контейнере) — полезен, чтобы проверить ветку на сервере,
не деплоя её.

Проще всего гонять и то и другое через глобальный скилл `/conductor`, если он
настроен на машине разработчика.

### 5.4 После деплоя

```bash
curl -s -o /dev/null -w "health: %{http_code}\n" http://216.57.108.107/     # 200
```

**Про миграции схемы — частая ошибка в рассуждениях.** Startup-хук
`_start_auth_poller` НЕ вызывает `init_schema`. Схему мигрирует `get_conn`
(`backend/deps.py`) на **каждом** запросе к `/api`, поэтому новые колонки и
таблицы доезжают при первом же обращении. Но если проверять прод-БД «голым»
`db.connect()` без `init_schema` — увидишь старую схему и решишь, что сломано.
Безопасно и сразу (идемпотентно):

```bash
docker exec ir-storyboard-backend-1 python3 -c \
  "from ir_storyboard import db; db.init_schema(db.connect('/app/data/matrix.db'))"
```

### 5.5 Обязанность после деплоя: вести паспорт

Оркестратор сам вехи не двигает — это работа того, кто катил. Сразу после
значимого деплоя:

```bash
curl -s -X PATCH http://localhost:5050/ui/api/projects/ir-storyboard/state \
  -H "X-Api-Key: $ADMIN_API_KEY" -H 'Content-Type: application/json' -d '{
  "docPercent": 98,
  "milestones": [{"title": "...", "done": true}, ...]
}'
```

`milestones` — **полная замена**: сначала прочитать текущий список
(`GET .../projects/ir-storyboard`), потом отправить его же плюс изменения.
Здоровье и даты деплоев Conductor пишет сам — руками не трогать. Стадию
(`stage`) двигать только при реальной смене (`staging` → `prod`).

Если за сессию был деплой, а вехи не тронуты — это пропущенный шаг, а не мелочь:
именно так паспорт превращается в вымысел.

### 5.6 Если всё сломалось

Откат — не «задеплоить прошлый коммит», а восстановление данных. Полный runbook:
**`docs/restore.md`** (три сценария, где какие копии лежат, что проверено).
Короткая версия: копии снимаются каждую ночь и уезжают в облако; на сервере есть
`./scripts/restore.sh` — он покажет доступные снимки и зальёт выбранный.

## 6. Инструкция для Claude Code

Эта секция — то, что должен соблюдать агент в сессиях по этому репозиторию.
Основной источник правды — `CLAUDE.md` в корне; здесь то, что важно именно при
появлении второго разработчика.

### 6.1 Начало каждой сессии (boot sequence)

1. `NEXT.md` — оперативное состояние: что сделано, что открыто, что следующее.
2. `git log --oneline -15` — правда о том, что было сделано на самом деле.
3. `git diff --stat HEAD` + `git ls-files --others --exclude-standard` — реальные
   изменения. **`git status` не доверять** в sandbox-окружениях с FUSE-mount: он
   выдаёт «Resource deadlock avoided» и ложно помечает файлы изменёнными.
4. `CLAUDE.md` — инварианты и конвенции.

Затем одной фразой сказать пользователю: «Где остановились: …, следующий шаг: …».
Без портянки.

### 6.2 Что делать

- **Уточняющий вопрос — ОДИН и подождать.** Не плодить варианты «а можно так, а
  можно эдак».
- **Тесты до коммита**: `pytest tests/ -m "not network"`.
- **Коммиты**: `<series-N>: <subject>` для серий (`task-3:`, `llm-5:`),
  `fix:` / `feat:` / `perf:` для одиночных. Сообщение объясняет **почему**, а не
  пересказывает диф.
- **В конце сессии обновить `NEXT.md`** — overwrite, не append: это снимок
  состояния, а не журнал.
- **После деплоя обновить паспорт** (§5.5).
- **Долгие LLM-вызовы (>~45 c: аудит, гайд, дедуп) — фоновым job-ом**
  (`_start_llm_job` + `GET /jobs/{id}`, на фронте `api.runJob`), не синхронно:
  NAT/файрвол рвёт простаивающее соединение примерно на 60-й секунде.

### 6.3 Чего НЕ делать

**Данные и инварианты:**
- ❌ **Не UPDATE-ить текст или snippet факта.** Факты иммутабельны: «изменение» =
  новый факт с новым `captured_at`, старый остаётся. Это несущий инвариант, на
  нём стоит вся история карточки.
- ❌ **Не заводить новые классы `Channel`.** Каналов ровно четыре. LLM Report
  Ingest и YouTube Ingest — оркестраторы поверх них, а не пятый и шестой канал.
- ❌ **Не заполнять L1–L3 из веб-источников.** Эти слои — только
  `offline_interview` (и `online_interview` как исключение, когда LLM-отчёт
  цитирует интервью с фаундером). Веб-факт в L1/L2/L3 → `skipped` с warning.
- ❌ **Не вешать `DELETE CASCADE` на work_items при удалении фактов** — закрытый
  факт должен оставлять след в work-item-е, который он закрыл.
- ❌ **Не тащить Alembic.** Миграции — только идемпотентные `ALTER TABLE` в
  `db.init_schema` (детектить колонку → добавлять).
- ❌ **Не чистить клиента `gonka`** — кластер Хачуяна оставлен намеренно как
  живой тест на бдительность аналитика.

**Код:**
- ❌ **Не писать локальный `json.loads(raw.strip("\`"))`.** Любой разбор
  LLM-JSON — только через `llm.generate_json` / `llm.extract_json`. Этот баг уже
  выгребали из шести мест.
- ❌ **Не вводить новые стейт-менеджеры и UI-киты** на фронте. Только react-query
  и Tailwind; эталон стиля — `PunchListView.tsx`.
- ❌ **Не редактировать заархивированные спеки** (`CLAUDE_TASKS*.md`,
  `*_SPEC.md`, `LLM_REPORT_PROMPT_TEMPLATES.md`) без явной причины — это
  исторический контекст. Новый объём работы = новый файл или серия коммитов.

**Инфраструктура:**
- ❌ **Не деплоить руками по SSH.** Только workflow.
- ❌ **Не коммитить на серверах.**
- ❌ **Не подтверждать ворота (Approve)** без явного «да» пользователя.
- ❌ **Не пушить вслепую в общие ветки.** Перед push — `git divergence`; при
  расхождении **rebase** поверх origin, не force и не merge вслепую.
- ❌ **Не двигать вехи паспорта задним числом** и не придумывать их — отмечать по
  факту, сразу.

## 7. Ветки: как работать вдвоём

До сих пор в проекте был один разработчик и одна ветка `feat/v2`, куда коммитили
напрямую. **Вдвоём так нельзя**: `feat/v2` — это то, что деплой тянет на прод, и
любой промежуточный коммит второго разработчика уезжает в бой при первом же
деплое первого.

Предлагаемая схема — минимум церемоний, но без этой дыры:

```
feat/v2          ← интеграционная ветка, ТОЛЬКО из неё деплой; всегда зелёная
  └── feat/v2-<тема>   ← короткоживущая ветка под задачу
main             ← зеркало feat/v2 (нужно только чтобы GitHub показывал свежий README)
```

Порядок работы:

```bash
git checkout feat/v2 && git pull --rebase
git checkout -b feat/v2-monitoring-filter        # ветка под задачу

# ... работа, коммиты ...

.venv/bin/python -m pytest tests/ -m "not network" -q
git fetch origin && git rebase origin/feat/v2    # подтянуть чужое ДО слияния
git checkout feat/v2 && git merge --ff-only feat/v2-monitoring-filter
git divergence && git push origin feat/v2
git branch -d feat/v2-monitoring-filter
```

Правила:
- **В `feat/v2` попадает только зелёное и законченное** — она деплоится как есть.
- **`--ff-only`** держит историю линейной; если не проходит — сначала rebase.
- **`main` не трогать вручную**, он подтягивается за `feat/v2` fast-forward'ом
  (`git push origin refs/remotes/origin/feat/v2:refs/heads/main`).
- Крупная фича, которая живёт неделями, — держать в своей ветке и регулярно
  ребейзить на `feat/v2`, а не вливать полусырой.

> 📌 **Про «версию 2» — уточнить у владельца до старта.** Ветка называется
> `feat/v2`, но это текущая боевая линия, а не «вторая версия продукта». Если
> задумана действительно новая версия, называть её ветку `v2` — гарантированная
> путаница в разговоре, в деплое и в этой инструкции. Договориться об имени
> заранее.
